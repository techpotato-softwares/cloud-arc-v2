Shared Singleton Strategy

Critical: Singletons loaded once in shell, marked singleton: true in Vite Federation config. Any MFE declaring the same package reuses the shell copy. Breaking this causes duplicate React contexts, dual query caches, and hook errors. Enforced via automated bundle analysis check in CI on every PR — build fails if a singleton is duplicated.

Chapter 06
Database Schema — All Tables

Isolation: Schema-per-tenant in PostgreSQL. public schema holds only tenants and feature_flags. Every other table lives in tenant_{uuid}. Row Level Security is active on all tables, enforced independently of application code. Audit log has RLS blocking DELETE and UPDATE — append-only at the database level.

Conventions: All PKs are UUID (gen_random_uuid()). Timestamps are TIMESTAMPTZ. Soft deletes: deleted_at TIMESTAMPTZ NULL — never hard-delete business records. Optimistic locking: version INT incremented on every UPDATE. All money: NUMERIC(12,2) — never FLOAT.

Chapter 09
Warehouse & Serial Tracking Architecture

Every solar panel in a SolarOS warehouse is tracked at two levels: mother serial (pallet QR) and child serial (individual panel barcode). The system maintains an unbroken traceability chain from purchase order → GRN → stock reservation → dispatch → customer delivery — fully queryable via the Serial Number Traceability Report.

📦 Mother Serial (Pallet QR)

Each pallet has one QR sticker from the manufacturer (e.g., Waaree). Scanning the pallet QR in the warehouse app auto-populates all child serials if the vendor's QR encodes structured data. Stored in pallets.mother_serial. Default 30 panels per pallet — configurable per product.

🔢 Child Serials (Panel Barcodes)

Each panel has its own barcode. If pallet QR doesn't auto-populate child serials, the warehouse executive scans each panel individually or pastes a CSV from the vendor packing list. Stored in serial_numbers table linked to pallets.id and inventory_items.id.

Chapter 12
Security Architecture — Zero-Trust

Five independent tenant isolation layers. Bypassing one does not bypass the next. Even a fully compromised application service cannot read another tenant's data — RLS operates at the database level, independent of all application code.

1
Network Perimeter — AWS WAF + TLS 1.3
All traffic enters via API Gateway HTTP v2 with WAF: OWASP Top 10, SQL injection, XSS, bot control. TLS 1.3 enforced at CloudFront and API Gateway. HSTS headers on all responses. Rate limiting by plan tier (Starter: 100 req/min, Enterprise: 5,000 req/min). No HTTP — any unencrypted request is rejected.
2
Authentication — Lambda Authorizer + JWT RS256
Every API call passes through the Lambda Authorizer before routing. Verifies JWT using RS256 public key from auth-service/.well-known/jwks.json (cached 15 minutes in authorizer memory). JWT payload: {userId, tenantId, roles, entitlements, plan}. Verified headers (X-Tenant-Id, X-User-Id, X-Roles) injected — services trust them implicitly. WAF blocks direct header injection attempts from external clients.
3
Application Layer — Tenant Context Middleware
Every Hono/Fastify service reads X-Tenant-Id from the verified request header. The tenantMiddleware from @solaros/auth-client executes SET search_path TO tenant_{id}, public on the PostgreSQL connection before any Prisma query. All subsequent queries in that request run scoped to the tenant schema. Service code never constructs schema names from user input — the tenant ID always comes from the verified JWT header.
4
Database — PostgreSQL RLS (Final Guard)
Row Level Security active on every table: USING (tenant_id = current_setting('app.tenant_id')::uuid). RLS operates independently of application code — even if middleware is bypassed, RLS filters all rows silently. Audit log has: FOR DELETE USING (false) and FOR UPDATE USING (false) — append-only enforced at DB level. Lambda IAM roles: SELECT/INSERT/UPDATE/DELETE only — no DDL, no TRUNCATE, no DROP schema.
5
Data — PII Encryption + S3 Presigned URLs
Sensitive fields (phone, GSTIN, PAN, bank details) encrypted with AES-256-GCM using per-tenant KMS key before storage. RDS encrypted at rest (KMS). S3: SSE-S3. All document URLs presigned with 15-minute expiry — no public S3 URLs exist anywhere in the system. Customer portal sessions: 4-hour JWT + OTP refresh flow. All portal visits logged in audit_logs.

Every response uses the same envelope: data (payload or null), error (error object or null), meta (page, limit, total, request_id, timestamp). On success: data has payload, error is null. On failure: data is null, error has code, message, and optional field for validation errors.

🔢 Pagination

All list endpoints: ?page=1&limit=20&sort=created_at:desc&filter[status]=Active. Meta always returns page, limit, total, has_next_page. Cursor-based pagination available for high-volume tables (serial_numbers — up to 1M rows per tenant).

🔒 Optimistic Locking

All PUT/PATCH requests must include version field matching current DB version. If mismatch → 409 Conflict with current version in response. Client re-fetches and retries. Prevents concurrent overwrites on quotations, sales orders, and customer records.

🔀 API Versioning

All routes: /v1/*. Breaking changes introduce /v2/*. v1 maintained 12 months post v2 launch. Deprecation announced via Deprecation: true and Sunset: YYYY-MM-DD response headers. Mobile GraphQL uses schema @deprecated directives.

🏷 ID Format

All internal PKs: UUID v4. Display IDs (SO-2026-000001, ENQ-2026-000001) generated in service layer using number series config from tenant.config. Display IDs for UI only — API calls always use UUIDs as identifiers.

⏱ Idempotency

All POST mutations accept optional Idempotency-Key header (UUID). If same key seen within 24h (Redis TTL), original response returned without re-executing. Critical for E-Invoice generation — prevents duplicate GSTN submissions on network retry.

Zoho Books GST Integration — Phase 1 Strategy

Rather than pursuing direct GSTN ASP/GSP registration in Phase 1 (which takes 4–6 weeks and requires significant compliance overhead), SolarOS will integrate with Zoho Books as the GST compliance layer. Zoho Books is already a certified GSTN ASP and handles E-Invoice (IRN generation) and E-way Bill natively. SolarOS acts as the source of truth for all business data and delegates GST document generation to Zoho Books via its REST API + webhook callbacks.

Phase 1 vs Phase 2 GST Strategy
Phase 1 (Months 1–8): Zoho Books integration via REST API + webhooks. SolarOS pushes invoice data to Zoho Books → Zoho generates IRN + E-way Bill → webhooks deliver results back → SolarOS stores IRN and serves documents. No GSTN registration needed from SolarOS side.
Phase 2 (Months 9+): Replace Zoho Books with direct GSTN ASP/GSP integration (own gst-service). Zero code changes in invoicing-service — only the gst-service implementation swaps. All stored IRNs, E-way Bills remain valid.
